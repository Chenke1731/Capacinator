# UI 预检协议

依据 [docs/UI_GENERATION_CONTRACT.md](../../../docs/UI_GENERATION_CONTRACT.md)（五支柱 A 计算可信 / B 语义透明 / C 决策流就绪 / D 呈现健壮 / E 操作安全）。用户用浅色主题。

## 生成前（写代码之前）

1. **判定触及面**：列出本次改动触及的支柱（A-E）与页面。同页被波及的旧交互也算触及面。
2. **状态矩阵规范（机器 dump，2026-10-11 机制改造）**：
   - 先渲染控件**草稿**（可以只有 DOM 骨架），跑 `npm run verify:states -- --quick` 让检查器 dump 元素骨架——**元素轴来自机器（闭包），人只填决策列**；手写元素清单=把"声明子集"盲区复发进规范。
   - 人工填每格决策：`元素 × {静态,悬停,聚焦,按下,禁用} × {浅色,深色}` 的样式意图（压掉全局规则/声明继承/阈值）。
   - "完成"的定义 = 声明格 ⊆ 检查器已行使格（或显式标注人工格）。交付对账物 = 检查器输出的已行使矩阵格报告。
3. **全局规则 dump**：grep 出 index.css / design-system.css 中作用于该元素类型的全部元素级规则（含 `:hover/:focus/:active` 态），逐项决策"压掉或声明继承"——**凡设背景/文字色的类样式按钮必须自带 :hover/:active 重声明**（全局 `button:hover` 特异度 (0,1,1) 压过单类 (0,1,0)，悬停隐形事故的机制）。
4. **FMEA-lite**：对每根触及支柱列 1-3 个潜在失效模式与设计对策（表格，5-10 分钟）。从"功能会怎么失效"推，不从"以前怎么失败过"推。
5. **Pre-mortem**：一句话回答"假设两周后用户为这个功能发了红框截图，最可能在圈什么？"取最可能的三个答案变成设计约束。
6. **红线速查**：
   - 自定义控件先查 client/src/index.css 与 client/src/styles/design-system.css 的元素级规则（button 默认 padding/背景/44px 命中）并显式重置；定宽按钮同块必写 padding；写完跑 `npm run lint:ui`。
   - **新浮层/选择器控件优先用已装的 Radix 原语**（dropdown-menu/select/dialog/tabs/toast）——碰撞翻转/键盘/焦点/a11y 免费；手写浮层仅限 useCellPopover 同族扩展。
   - 视觉决策过契约"视觉战术速查"八条与 Okabe-Ito 默认色板（类别编码专用，同屏 ≤4 色）。

## 交付前（跑守卫之前）

1. **全称状态检查器**：`npm run verify:states`（交付全量；迭代用 `--quick`）——自动枚举全部可见交互元素×{静态,悬停,聚焦,禁用}×双主题，断言对比度（文字≥4.5/边界≥3）/命中≥24px/零遮挡/零越界/字号∈令牌集/浮层贴锚。红了当场修（写码时修是秒级，交付时修是轮次级）。
2. **认知走查**：浅色+深色渲染改动页面，**逐个完整执行一次末端操作**（点最后一项/最远按钮——"看一眼"不算走查），每步四问：
   1. 用户此刻想产生这个效果吗？
   2. 用户能看到这个操作吗？（含**每个交互态**的物理呈现——悬停/聚焦/禁用下文字是否可读）
   3. 用户能把操作和效果联系起来吗？（知道它在改什么、范围、后果）
   4. 操作后能看到反馈吗？（值变化/受影响量/失败提示）

任何一问为"否"→ 回到生成前修，不进守卫。走查通过后才跑 verify:boards（已收编状态检查器）/ verify:visual / 单测（守卫是兜底不是防线）。检查器自身健康用 `npm run verify:states:selftest` 定期验证（注入坏规则必须红）。

## 失败归位

用户指出的问题按支柱归位：违反已知维度 → 补守卫断言；支柱没覆盖 → 修契约推导缺口，并把这次失败加进佐证表。新教训先问"它能落在哪一层拦截"（行动=hook／渲染=全称检查器／语义=测试／构建=pre-commit），写进记忆的行动规则=没写。
