# Capacinator 落地需求确认单(v2 · 经拷问修订)

> 基于 2026-09-20 多轮需求澄清 + grill-me 拷问(两轮 8 问),最终确认版。
> 本文档是系统配置与二次开发的依据;与《使用说明书》(docs/USER_MANUAL_zh-CN.md)配套。
> **v2 修订摘要**:删除虚构角色;估算偏差区间化;校准机制如实降级;补 Plan B;明确排产权、小事处置、成功判据。

## 1. 角色与组织

- **使用者定位**:开发交付领域人力资源主管(有事情排序决定权),关注人力消耗安排(非进度跟踪)
- **团队规模**:中型,10–30 人,并行事情 5–15 件
- **角色构成(拷问修正)**:**设计(SE)与开发两类**。~~产品/需求分析~~ 独立角色不存在——**SE 全包需求分析+方案设计+评审参与**
- **SE 是最稀缺资源**:1:5–1:8 的薄层人力承担全部需求分析、设计、评估评审;**设计人力不足已实际发生过**(拖累交付/拒过需求),是急症而非预防性保健
- **人员形态**:专岗为主,少量多面手可跨池
- **数据维护**:开发侧由人力主管维护;设计侧理想由 SE 自行维护,**Plan B:SE 不配合则人力主管代维护兜底**(代价:数据粒度与及时性下降)

## 2. 事情分类与工作量机制

| 事情类型 | 工作量机制 | 系统落法 |
|---|---|---|
| **需求类**(可估) | SE 分析后给**代码行预估** → 按 **0.5k 行/人月** 折算开发人月;SE 的设计/分析工作量先按开发人月 **~25% 占位**(含需求分析,因为 SE 全包),评审时逐步替换为真实值 | 设计+开发两阶段建模;结构化评估记录(第 1 步) |
| **问题单**(难估) | 数量驱动预留:按月看单量定比例,起步 30% | 常驻条目,按月可调 |
| **项目事务** | 固定预留,起步 25–30% | 常驻条目,全员 |
| **琐碎小事**(拷问新增) | **不进排期**:重要的小事在系统留痕(轻量类型,仅记录);琐碎的随手做,由事务缓冲天然覆盖 | 轻量项目类型,不参与排期分析 |

**估算偏差(拷问修正)**:0.5k 行/人月的实际偏差 **±20–50%(SE 自评,视事情类型)**。因此:
- 所有排期/死线分析输出必须**区间化**("缺口 1–3 人月"、"最早 X–Y 月交付"),禁止单点伪精确
- 缓冲设计要吸收方差(按偏保守侧配置)
- **费率校准进第 1 步**:事情交付后回填实际人月,滚动收窄费率区间

**校准机制(拷问降级,如实描述)**:无工时填报,问题单/事务的实际消耗**没有硬数据**,校准依赖**间接信号**——单子积压/挤占需求工作=预留不足,连续宽裕=过预留。该方法可行但有噪声、慢热,需 2–3 个月才形成初步换算率。

**评估流程**:小会评审,SE 初评(代码行+设计粗估)作为输入,结论落评估记录;无正式审批流。

**关键事实**:问题单(20–40%)+事务(25%+)≈ 开发人力 45–65% 被常驻消耗,**真实可排产能约为人数的 ~45%**。

## 3. 交付时间分析(四种,按月颗粒,输出区间)

1. **死线校验**:给定截止日,输出各角色逐月缺口区间与缺口月份
2. **反推交付日**:人力固定,推算事情最早可排入月(区间)
3. **多事排期权衡**:调优先级顺序,看不同排法对各事交付时间的影响(用户有排产权,结论可直接执行)
4. **设计/开发分节点**:设计完成截止时间为开发启动前置节点,分别评估

**衔接模式**:设计→开发视事而定(串行/重叠/并行皆有),不做硬约束。
**人力不够的杠杆(常用序)**:重新排序 > 降范围 > 加人/借人 > 延期;期望有方案对比沙盘。

## 4. 分发与监控

- **分发**:人工指定;系统提供信息支撑(负荷水位、超载预警、影响预览)
- **核心输出**:设计(SE)与开发各自的总消耗/剩余/缺口(按月);扣缓冲后真实可用产能;**设计人力不足提前预警**(已发生过,急需)
- **明确不要**:进度跟踪、任务看板、工时填报

## 5. 系统满足度结论(不变项摘要)

事/人分开 95% · 按角色看消耗 95% · 混合粒度 85% · 容量预留 90% · 分发支撑 90% · 评估记录 40%(第 1 步) · 死线校验 30%(第 1 步) · 反推交付日 0%(第 2 步) · 排期权衡 35%(第 2 步) · 设计工作量显式化 40%(配置+第 1 步)

## 6. 落地路径

**第 0 步 · 纯配置(1–2 天)**
1. 角色字典:**设计(SE)、开发** 两类(无产品角色)
2. 项目类型:「需求类」(设计+开发阶段,设计配比 25% 占位)、「问题单支持」(常驻)、「项目事务」(常驻)、「零星事项」(轻量留痕,不排期)
3. 常驻缓冲:开发挂问题单 30%、全员挂事务 25%(按月可调,偏保守侧)
4. 导入真实人员(按 1:5–1:8 补 SE)与存量事情
5. SE 侧自行维护设计分配;不配合则人力主管代维护
6. 试运行 2–4 周,**成功判据:设计/开发消耗报表在小会上被真实用于讨论**(不是"系统有人登录",是"报表影响了一次决策")

**第 1 步 · 小开发(1–2 周量级)**
- 评估记录:SE 录代码行 → 0.5k/人月折算(费率可配)→ 设计人月比例占位可改 → 评审备注+期望交付
- 死线校验一键分析(区间输出,基于扣缓冲产能)
- **交付后回填实际人月,滚动校准费率与设计占比**

**第 2 步 · 中开发(视第 0 步体验决定)**
- 排期沙盘:月度桶推演、拖序重排、方案对比(重排/加人/延期),全部区间输出
- (可选)问题单量登记+滚动平均建议预留比例

## 7. 风险与依赖(拷问后修订)

| 风险 | 应对 |
|---|---|
| SE 侧不配合录入 → 设计黑盒依旧 | Plan B 代维护兜底;同时用"SE 也能看到自己负荷/工作留痕"争取配合 |
| 估算偏差 ±20–50% → 排期伪精确 | 区间输出;保守缓冲;第 1 步回填校准 |
| 无实际消耗数据 → 缓冲校准慢且有噪声 | 接受间接信号法;2–3 个月才出初步换算率,预期管理 |
| SE 全包(分析+设计+评审)→ 单点瓶颈 | 设计可见性本身就会暴露此问题;若坐实,向管理层要人的论据即来自报表 |
| 无人愿维护数据 | 成功判据直接绑定"报表被真用";若 2–4 周内小会不用报表,先解决使用意愿再谈第 1 步 |
| 预置/E2E 数据与真实数据并存 → 报表误读 | 先保留参考;正式试运行前清理或归档 E2E 数据(第 0 步收尾动作) |

## 8. 术语映射(实施前审视,已裁决)

| 你的领域术语 | 系统配置(最终) | 说明 |
|---|---|---|
| SE(需求分析+设计全包) | 角色「**SE**」 | 命名按团队日常叫法 |
| 开发 | 角色「开发」 | |
| 测试 | 角色「测试」(**仅字典预留,不跟踪消耗**) | 测试有独立人力但不在本系统跟踪;阶段模板保留测试阶段作时间节点,但**零角色配比**——避免产生虚假缺口告警 |
| 需求类事情 | 项目类型「需求交付」:需求分析/设计 → 开发 → 测试(时间占位) → 交付 | |
| 问题单 | 常驻项目「[预留] 问题单支持」 | 报表语义=产能扣减,非业务需求 |
| 项目事务 | 常驻项目「[预留] 项目事务」 | 同上 |
| 重要零星小事 | 项目类型「零星事项」(无阶段,不排期) | |
| 人月 | 分配比例×月(1 人月=1 人 100% 挂满一月);报表 FTE/工时按此换算 | 培训口诀 |
| 排产权 | 项目优先级 高/中/低 | |
| 方案对比 | 场景(基线/分支/合并) | |

**术语陷阱备忘**(培训/沟通用):
- 系统有两个"角色":人员页的资源角色(我们的 SE/开发/测试)与设置页的**系统权限角色**,互不相干——沟通时后者只叫"系统权限"
- "项目"一词泛化承载事情/预留条目,预留类必须带「[预留]」前缀
- 规划者(Planner)标记:人力主管与 SE 侧需要,普通开发不需要
- 财周格式仅在 Excel 导入模板出现,按月规划可无视

**预置数据处理(已裁决)**:当前库中 E2E 测试残留与种子预置数据**先保留作参考**,我们的字典新建并存。⚠️ 注意:正式试运行前需清理或归档 E2E 数据,否则仪表盘/报表会混入 E2E 项目与人员造成误读(列入第 0 步收尾动作)。
