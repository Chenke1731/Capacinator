# UI 生成契约（Generation Contract）v2

> **推导顺序**：先从"这个项目本身是什么、支撑什么决策"演绎出设计支柱（覆盖全部应有的维度），
> 历史失败只作为各支柱下的佐证与校准（它们是维度被违反过的实例，不是维度的来源）。
> 失败归纳清单的致命伤：覆盖面恰好等于已发生过的意外，而失败空间远大于踩过的坑。
>
> 维护规则：①支柱结构只随项目本质演进（如新增协作场景才动支柱）；②每次"用户看见而我没看见"
> 的失败，归位到某根支柱下作佐证，并检查该支柱的推导是否有缺口要补。

## 项目本质与推导

**本质**：交付领域人力主管用一个工具代替 Excel 管理交付线的人员排布。工具的全部价值
= 通过它做出的排产决策【正确、快、有把握】。

| 价值要求 | 推导出的支柱 |
|---|---|
| 决策正确 → 计划状态必须是真的 | **A 计算可信** + **B 语义透明** |
| 决策快 → 排产是"看→调→看后果→再调"的循环 | **C 决策流就绪** |
| 有把握 → 真实环境下不撒谎、操作不出事 | **D 呈现健壮** + **E 操作安全** |

## 三层防线模型

| 层 | 时机 | 干什么 | 性质 | 业界方法来源 |
|---|---|---|---|---|
| ① 生成契约 | 写代码前/中 | FMEA-lite 支柱失效排查 + pre-mortem 推演 | 前置（演绎） | FMEA；Pre-mortem (Klein) |
| ② 认知走查 | 交付前，跑守卫前 | 双主题渲染 + 认知走查四问，人眼看 | 前置（补演绎盲区） | Cognitive Walkthrough |
| ③ 守卫 | 交付时 | verify-boards / verify:visual / lint:ui / 单测 | 兜底 | 启发式评估的机器化 |

## 生成前协议（第①层的工作步骤）

**1. FMEA-lite 支柱失效排查**（失效模式与影响分析，汽车/航天可靠性工程）：
从功能出发问"会怎么失效"，不从事故出发。对本次触及的每根支柱，列 1-3 个潜在失效
模式与设计对策，5-10 分钟。模板：

| 触及支柱 | 潜在失效模式 | 设计对策 |
|---|---|---|
| 例:D3 呈现健壮 | 全局 button padding 吃光定宽按钮内容盒 | 同块显式 padding; lint:ui |
| 例:A2 新鲜度 | 编辑池后详情页/看板仍显示旧值 | invalidate 覆盖全部消费方清单 |

**2. Pre-mortem 推演**（事前验尸法，Gary Klein）：写代码前一句话回答——
"假设两周后用户为这个功能发了红框截图，最可能在圈什么？"把最可能的三个答案变成
设计约束。这是对演绎盲区最便宜的探针。

## 五支柱维度表

每条 = 支柱要求 + 生成时怎么查。〔斜体〕为该维度被违反过的历史佐证。

### A 计算可信 —— 数字就是产品本身，错的数字比没有工具更糟

- **A1 聚合正确**：池+实名、暂停排除、跨侧汇总算对；聚合逻辑改动必须带服务端测试。
- **A2 新鲜度**：任何编辑后，所有受影响的数字立即反映——invalidate 覆盖全部消费方
  （列表/详情/看板/告警）；写方防共享键投毒（`Array.isArray(payload) ? payload : payload?.data || []`）。
- **A3 单位一致**：FTE / % / 人月 / 人数全站同单位同符号，展示处标单位。
- **A4 边界数值**：0、空、负载>100%、池全未实名、负值——退化状态数字不崩、界面不骗
  （空白与 0 要可区分；超载要有视觉语言）。
- **A5 规模退化**：数据量 ×10（项目/人员/分配）时计算与渲染不塌；批量接口不分页拉全量的要有上限意识。

### B 语义透明 —— 不看文档能读懂计划状态

- **B1 域语言统一**：实名/池、设/开、RP 节奏、P 档——同一概念在列、气泡、详情、语言包
  同一套词与视觉编码。〔"列与气泡术语不同构"教训〕
- **B2 自标注**：每个数字带单位/标签；每个编辑控件声明"改什么、步长、后果"；
  "此处改什么、别的去哪改"一句话说清。〔"完全没办法知道编辑逻辑"事故〕
- **B3 状态可预测**：推进状态/执行编辑前，用户能推断哪些数字会变、方向如何
  （至少在 tooltip/气泡里说明影响面）。
- **B4 告警可读**：黄牌告警的触发规则能从界面理解（为什么亮、怎么消）。

### C 决策流就绪 —— 界面就是"看→调→看后果→再调"循环本身

- **C1 就地性**：高频操作落在列表页本体，零弹窗；"要先点进详情才能做"的高频操作是交互债。
  〔弹窗流教训〕
- **C2 回路速度**：从一个排产问题到答案的点击数最少（搜人→看负载→分配一屏内完成）；
  首屏密度服务决策不服务美观。〔工具栏吃掉 520px 首屏教训〕
- **C3 后果可见**：每次调整后，受影响的量（对侧负载、告警、分组位置）就地反馈——
  行 flash/组头高亮只是起点，终极是调整点旁边能看到关键后果。
- **C4 视图组织服务排博弈**：分组（版本）、排序（P 档）、筛选的逻辑要能讲出决策含义。

### D 呈现健壮 —— 工件必须在自己所处的渲染环境里真实存在

- **D1 双主题物理渲染**：浅色+深色各渲染一次并亲自看；用户用浅色。〔两轮白干教训〕
- **D2 视口矩阵**：1600 与 1366 各过；断点行为（如 <1440 隐藏列）是有意的。
- **D3 全局规则兼容**：自定义控件前先查 index.css / design-system.css 元素级规则
  （button 默认 padding/背景/44px 命中）并显式重置；**定宽按钮同块必写 padding**
  （`npm run lint:ui` 静态拦截）。〔加减号零宽物理消失事故〕
- **D4 物理可见**：图标 rect 宽高>0、文字与底色可辨；按钮盒达标 ≠ 内容可见
  （verify-boards 有塌陷检测，但设计时就要保证）。〔同一事故：命中/axe/碰撞三层全免疫〕
- **D5 盒子防御**：定宽容器装可变内容 → min-width + flex:none；行级信息不塞定宽构件内部。〔chip 溢出重叠事故〕
- **D6 i18n 完备**：新键 zh-CN 与 en-US 同时添加，禁裸键。〔tags.manage 裸键〕
- **D7 键盘可达**：Enter 确认、Esc 取消、点外关闭、Tab 移动。

### E 操作安全 —— 排产动作不能出事故

- **E1 防误触**：同值再点=无操作；破坏性操作二次点击确认；步进有上下限。
- **E2 失败可见可重试**：请求失败有反馈，不留半完成状态；按钮 busy 态防重复提交。
- **E3 可逆或可修复**：优先可逆设计（池可步进回、标签可再勾掉）；不可逆的要有确认与后果说明。
- **E4 并发/脏状态**：多标签同编辑不静默覆盖（至少冲突时提示）；部分失败不写脏数据。

## ② 认知走查（交付闸，跑守卫之前）

Cognitive Walkthrough（认知走查，Polson/Wharton，可用性工程标准方法）：以第一次
见到此页面的人视角，沿真实任务逐步走（双主题渲染，逐个打开本次涉及的全部交互，
**含同页被波及的旧交互**），每步四问：

1. **用户此刻想产生这个效果吗？**（控件出现在任务的正确环节）
2. **用户能看到这个操作吗？**（物理呈现：图标、标签、悬停提示）
3. **用户能把操作和效果联系起来吗？**（不看文档知道它在改什么、范围、后果）
4. **操作后用户能看到反馈吗？**（值变了/受影响的量动了/失败了会怎样）

四问有一个"否"即回到维度清单修，不进守卫环节。

## ③ 守卫（兜底）

- `npm run lint:ui`——CSS 反模式静态扫描（定宽按钮无 padding 等），生成时秒级，`SELF_TEST=1` 自证
- `npm run verify:boards`——结构+几何+可供性断言（图标物理可见、塌陷检测、池标签、编辑模型声明）
- `npm run verify:visual`——像素基线 + axe 预算 + 碰撞，双主题×双视口
- 单测——交互语义与落库

## 业界方法引入与归位

| 方法 | 来源领域 | 在本项目的落点 |
|---|---|---|
| FMEA（失效模式与影响分析） | 汽车/航天可靠性工程 | 生成前协议第 1 步：支柱失效排查表（从功能推失效，非从事故推） |
| Pre-mortem（事前验尸） | Gary Klein，决策心理学 | 生成前协议第 2 步：红框截图推演 |
| Cognitive Walkthrough | 可用性工程（Polson/Wharton） | 交付闸：认知走查四问（取代原"陌生人三问"，Q1/Q3 补上"操作-效果关联"） |
| 启发式评估（Nielsen 十启发式） | 可用性工程 | 守卫的镜头来源：碰撞/物理可见/一致性/防错/状态可见各对应启发式的机器化；单评估者覆盖率有限，守卫按镜头分遍跑即为对策 |
| Poka-yoke（防错法） | 丰田生产系统 | 已有实践命名归位：同值无操作、min-width 代替 width、padding 同块重置、步进上下限、二次点击确认 |
| UX Honeycomb（credible 节点）/ Garrett 五层 | 信息架构/UX | 支柱推导的外部验证：honeycomb 的"可信"即 A 支柱"数字可信"；Garrett 战略→范围→结构→骨架→表面即"本质→支柱→维度→呈现"同构 |
| BDD/规格先行（Given-When-Then） | 敏捷工程实践 | 交互功能先写验收例再生成——单测先行已是其形态，契约点名归位 |

未引入及理由：QFD/House of Quality（面向大规模需求工程，单用户工具过重）；
遥测/A-B 测试（单用户无样本量）；完整十启发式人工评估（守卫已机器化其中可判定的子集，
人工全遍与守卫重复）。
