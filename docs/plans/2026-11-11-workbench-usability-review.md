## 1. 「工作台」的界定（两个层次）

- **狭义**：侧边栏第一项「仪表盘」`/dashboard`（`Dashboard.tsx`，372 行）——纯只读总览，唯一本地控件是日期范围选择器，其余交互全是「点卡片跳到别的页面」。
- **广义**：排产主管每天打开应用完成「需求进来 → 分流 → 排进迭代 → 派人 → 盯超载」的完整操作闭环，横跨 5 个页面 + 1 个弹窗。

本审视按**广义**讨论（便利性瓶颈全在广义链上），狭义仪表盘的改造（待办中心）作为开放问题挂 D20。

## 5. 已裁决 D19（2026-11-11 用户批准）：B8 收件箱终态可逆性

**术语对齐**（本次讨论确认）：

- **终态** = 三层锁死：① 无回头 API（convert/reject 都是 `WHERE status='new'` 条件更新，converted/rejected 无出边）；② 字段不可改（`IntakeService.ts:227` 明示 status/converted_project_id 不可改）；③ 不可删但留档（硬删除仅 new，`IntakeService.ts:284-290`）。这是刻意的审计设计：intake 行是「出生证明」，修正一律去改下游实体。
- **重建** = 误操作后的手工恢复，两种误操作现状不对称：
  - **误拒**：可重录。source_ref 查重排除 rejected（`IntakeService.ts:368` + DB 部分唯一索引同款），同 SR 重新录入不撞重复；代价是手工搬运 raw_text、审计上两条记录。
  - **误转**：烧号。事务里已建项目+阶段+生命周期事件；项目可删（需先清子项，`ProjectsController.ts:960`）但 intake 行永停 converted 指向死项目，且 converted **参与**查重（与 rejected 相反），重录同 SR 直接 409 `duplicate_source_ref`。
  - 一句话：**误拒可重录，误转烧号。**

**裁决内容**：

1. rejected → new 加 **reopen**（清 reject_reason + 审计事件；一端点 + 行上一按钮）。多角色下「拒绝理由=信息不足→补齐→reopen」是自然闭环，重录会丢 raw_text/来源时间戳且记录分裂。终态语义不破坏（converted 仍是终态）。
2. converted **不做 un-convert**：反向拆事务（项目+阶段+生命周期事件+回链，还要处理已有分配）复杂且危险。误转的类型/优先级错误改项目本体即可。
3. converted 行**死链防护**：跳转前校验项目存在，死了显示「项目已删除」而非死链。
4. **source_ref 释放**方案（删项目时连带处理或允许重录）→ 单独过 backend-review 后再立项。
